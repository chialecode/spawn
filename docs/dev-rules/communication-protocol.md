# 沟通协议、用户待办与 Swarm 消息板规范

本协议规范三类核心沟通界面：**Agent ↔ 用户汇报与待办同步**、**Agent A ↔ Agent B 跨轮次阶段交接**，以及 **Swarm 多智能体共享消息板（Message Board）点对点协同**。协同研发主流程见 [开发协作流程](development-workflow.md)。

---

## 1. Agent 对用户汇报与 `USER-ACTIONS.md` 唯一入口原则

<a id="agent-user"></a>

1. **用户事项唯一入口**：
   - 凡需要用户亲自执行的动作——包括**本机开发环境安装（`ACT-*`）、阶段推送/PR/合并等远端授权（`ACT-*`）、产品方向裁决（`Q-*`）、实机高刷/手柄体验检查（`H-*`）**——统一且仅在根级 [USER-ACTIONS.md](../../USER-ACTIONS.md) 维护当前有效状态。
   - 用户无需翻阅冗长的阶段计划、架构文档或 Swarm 内部消息记录即可直接操作待办；聊天回复仅需引用稳定编号（如“`ACT-001` 已完成”、“授权 `ACT-002`”），Agent 当轮同步回写 `USER-ACTIONS.md`、[已确认决策](../decisions/confirmed-decisions.md) 与受影响正本。
   - 属于编码实现、单元测试、开源适配或文档同步的工程事项一律记入 [集中工程事项台账](../decisions/open-questions.md)（`OSS-*` / `LOOP-*`），严禁混入 `USER-ACTIONS.md` 烦扰用户。
2. **阶段收尾对用户的标准汇报结构**：
   每次向用户交付阶段成果或报告关键节点时，保持精炼高密度，固定包含以下五项：
   - **实际完成结果**：本轮落地的核心模块、文档或修复清单（所有仓库文件附可点击链接）；
   - **真实门禁与证据**：实际运行的命令、环境版本与退出码（如 `python scripts/check_docs.py`、`git diff --check`、`dotnet test`），以及当前本地分支与完整 40 位提交 SHA；
   - **诚实未测边界（`not-run`）**：明确列出因待装 SDK、缺外部凭据或待实机体验而保持 `not-run` 的项目，绝不模糊冒充已通过；
   - **关联待办编号**：引用 [USER-ACTIONS.md](../../USER-ACTIONS.md) 中需用户关注的 `ACT-*` / `Q-*` / `H-*` 编号；
   - **唯一首选下一步**：给出明确、单一的推荐下一步动作（例如：需要跨会话交接时附可复制交接 Prompt；技术审查已收敛时请用户审阅并授权具体 `ACT-*`）。

## 2. Agent A ↔ Agent B 跨会话可复制交接 Prompt 规范

- **仅在真实需要切换角色时输出**：只有当 Agent A 完成整阶段规划需交由 Agent B 连续编码实现（A→B）、Agent B 完成全阶段自检需交由 Agent A 集中技术审查（B→A），或 Agent A 发现较大跨模块缺口需整批退回返工（A→B 返工）时，才在回复末尾附上一段可直接复制粘贴的 Prompt（标准结构见 [A/B 交接模板](../templates/agent-handoff.md)）。
- **必须包含的硬核锚点**：交接 Prompt 必须写明目标里程碑与计划版本（`docs/delivery/stage-plan.md`）、工作分支名、不可变阶段父提交 40 位 SHA、当前交付提交 40 位 SHA（或现场 `git rev-parse HEAD` 核验指令）、必跑门禁命令及严禁越界的远端操作红线；不把验收标准全文重复粘贴进 Prompt。
- **审查收敛后不再空转**：当 Agent A（或 Swarm 集群）已完成阶段实现与集中审查且零工程阻断时，直接进入请求用户授权 `ACT-*` 环节，禁止再机械生成一段无实际任务的交接 Prompt。

## 3. Swarm 集群共享消息板（Message Board）通信礼仪

<a id="swarm-board"></a>

在启用 Swarm 多智能体并行开发时，消息板（`read_board` / `post_message` / `swarm_wait`）是全体成员共享的公共上下文，每条消息都会消耗被唤醒成员的 Token 预算，必须严守以下通信纪律：

1. **`@name` 是唤醒门铃而非抄送（CC）列表**：
   - 处于 `swarm_wait` 休眠态的成员仅在消息包含 `@自身名称` 或 `@all` 时被唤醒（零休眠成本）。
   - **点对点交接原则**：完成本职任务后仅 `@` 下一步需要行动的同伴（例如：模块规格作者完成后 `@gov-rules` 核对注册表并 `@verifier` 提请验收；`@verifier` 验收全通后 `@git-github` 执行最终提交收束；`@git-github` 落盘核验后 `@coordinator` 汇总交付）。中间协作环节**严禁顺手抄送 `@coordinator` 或滥用 `@all`**。
2. **禁止寒暄与空洞附和**：
   - 严禁发送“收到”“开始工作”“准备就绪”等无实质产出的礼貌消息。Worker 领受明确 Brief 后直接埋头执行调研或编写，第一条发帖应当是**阶段栅栏就绪通知、跨边界问题澄清或附带精确产物清单的交付结果**。
3. **使用 `#seq` 序号引用前文**：
   - 引用消息板历史结论、SHA 锚点或审查清单时，直接写明消息序号（如“已按 `#24` 提供的第一提交 SHA 写入契约”、“已修复 `#29` 指出的 `F-01` 链接问题”），禁止大段重复摘抄前文。
4. **严防漏读休眠死锁**：
   - 调用 `swarm_wait(since=...)` 进入等待前，传入的 `since` 必须是自己**实际已通过 `read_board` 读过的最大消息序号**，绝不能盲传未读的队列头部序号，确保工作期间到达的新消息能立即唤醒自己；严禁用循环轮询 `read_board` 或 Shell `sleep` 代替 `swarm_wait`。
